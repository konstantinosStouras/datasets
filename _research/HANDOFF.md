## Resume checklist

1. Read this guide, METHODS and STATUS, then inspect Git status/remotes and fetch current remote state. Preserve unrelated changes.
2. Check the current verified catalog and review logs before researching a lead; deduplicate by DOI and dataset ID/provider release.
3. Review a small priority batch with actual sources and downloadable-file checks. Save unresolved leads and reasons as well as successes.
4. Add only verified components to `research-additions.json`; retain the original `dateAdded` when updating an existing entry, and update `verifiedAt` only after a new check.
5. Validate merge/schema/links, publish the fork, check the cloud workflow and public feed, then update STATUS with actual outcomes.
6. Report the new dataset names, papers and access limitations to the owner. Keep the Markdown handoff current; do not merely promise to update it later.

## Publishing data additions

The owner approved immediate publication and the existing keyless GitHub–Firebase connection. A push on `main` changing `research-additions.json` triggers `publish-catalog.yml`. It also runs hourly at minute 41. The independent upstream sync runs hourly; check its current workflow for details. These run in GitHub while the owner's computer is off.

The publisher parses `README.md`, merges `research-additions.json`, writes protected `datasetLinks` records to Firestore and commits sanitized public metadata. The frontend fetches `https://raw.githubusercontent.com/konstantinosStouras/datasets/main/catalog-public.json` on load, falling back to its bundled copy. Data additions therefore do not require a full website deployment.

Use explicit repository arguments, for example:

```sh
gh run list -R konstantinosStouras/datasets --workflow publish-catalog.yml --limit 5
gh run view RUN_ID -R konstantinosStouras/datasets
```

Inspect the exact changed paths before committing. Push normally; if a bot has advanced `main`, fetch and rebase only the intended clean local commits, resolving conflicts carefully. Never force-push. Confirm workflow success AND that the expected dataset IDs appear in the live public feed. A commit alone does not confirm publication.

Website layout/metadata changes are published separately to the site's `master` branch through GitHub Pages. This is a large repository and deployment can take several minutes. Read its repository instructions first. Preserve its public visibility and existing automation-compatible branch protections. Keep source research inputs under `datasets/_tools/` and backend files under `datasets/_backend/`; Jekyll excludes underscore directories. Refresh bundled fallbacks periodically, without replacing the live fork's newer data with a stale copy.

## Access model and operational boundaries

Public visitors can browse sanitized descriptions and paper metadata. Verified email accounts and Google sign-in users can read source/citation links, export results, save private bookmarks, and submit pending additions or edits. Contributions require owner review in Firebase. Google supplies a verified email identity; email/password accounts use Firebase verification messages.

The website gates its displayed links. The public GitHub sources and third-party providers remain independently accessible. Do not describe the underlying public datasets as globally private. Raw archives are not rehosted in Firebase Storage.

Publishing uses Workload Identity Federation restricted to this fork's `main` publishing workflow and service account `dataset-publisher@stouras-dataset-library.iam.gserviceaccount.com`. Do not store OAuth tokens or service account keys in docs/code. Do not rerun IAM setup for routine additions. Always explicitly name the Firebase project when deploying rules.

Keep the publisher copies of `catalog.mjs`, `research.mjs`, and `_backend/admin.mjs` aligned with site implementations if changing import behavior. The current import performs one Firestore write batch; implement chunking before reaching 500 records. It upserts entries; removing a catalog entry does not automatically delete an old Firestore link record.

## Website sharing and attribution

Sharing metadata is static in `datasets/index.html`, so crawlers do not need JavaScript or login. The branded `og-image.jpg` is 1200 × 630. Keep canonical and `og:url` identical, absolute HTTPS image URLs, one `og:image`, accurate dimensions/alt text, and the image small enough for messaging clients. Icons and the web manifest are site assets, not user data. Check live unauthenticated page/image responses after deployment; cached social previews may take longer to refresh. Never claim tests inside every messaging app unless actually performed.
